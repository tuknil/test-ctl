control-translation-service — DevOps handoff

Everything needed to build the container image and deploy this service to Azure Container Apps. A working Dockerfile, .dockerignore, and docker-compose.yml are already included in this repo as a starting point — adapt them to your standard CI/CD pipeline and Azure conventions. No Bicep/Terraform or CI workflow is authored by the app team in this handoff; that is DevOps-owned.

3. Dependency management

Dependencies are declared in pyproject.toml and managed with uv. Provided install commands:

uv sync                       # local/dev
# or, inside a container without uv.lock committed:
uv pip install --system -r pyproject.toml

If your org's build pipeline prefers pip + requirements.txt, the runtime dependency set is small and pinned in pyproject.toml: fastapi, pydantic, pydantic-ai, uvicorn, python-dotenv.

Included Dockerfile (summary)

The provided Dockerfile uses python:3.11-slim, installs dependencies via uv, copies src/ and ui/, sets PYTHONPATH=/app/src, exposes port 8000, and defines a container HEALTHCHECK against /health. Treat it as a working starting point — adjust base image, multi-stage build, and layer caching to match your org's hardened base images and registry scanning policy.

Secrets handling: the API key must be injected as an Azure Container App secret (or a Key Vault reference), never as a plain environment variable and never baked into the image or committed to source control. The app reads standard environment variables at runtime — it does not require a mounted .env file in production; DevOps can inject real environment variables directly via the Container App secret/reference mechanism.

5. Azure Container Apps requirements

  • An Azure Container Registry (ACR) to push the built image to.
  • A Container Apps Environment (with a Log Analytics workspace) to host the app.
  • Ingress: HTTP, target port 8000. External ingress only if the demo UI/API must be reachable outside the environment's private network.
  • Scaling: this is a stateless-ish service (in-memory run store only — see note below); min replicas can be 0–1, max replicas per your standard sizing for a lightweight FastAPI service.
  • Secrets: configure the model API key as a Container App secret and reference it in the container's env var list (e.g. OPENAI_API_KEY → secretref).
  • Health probe: point liveness/readiness probes at GET /health.
Known limitation to flag internally: run results are stored in an in-memory dictionary inside the process. If Container Apps scales to multiple replicas or restarts the container, GET /runs/{run_id} lookups will not be consistent across replicas/restarts. This is acceptable for a demo/POC deployment; flag it if persistent run history is required — the app-side follow-up is a durable store swap (see docs/assumptions-and-followups.md in the repo).

6. CI/CD

No pipeline YAML is authored by the app team. Suggested pipeline shape for your standard tooling (GitHub Actions / Azure DevOps / other):

  1. Checkout repo.
  2. docker build -t <registry>/control-translation-service:<tag> .
  3. docker push <registry>/control-translation-service:<tag>
  4. az containerapp update --name <app> --resource-group <rg> --image <registry>/control-translation-service:<tag> (or your org's standard Container Apps deployment task).

7. Local verification before handoff

To sanity-check the image locally before pushing to a registry:

docker compose build
docker compose up
curl http://localhost:8000/health
