ℹ️ How it works & what each example means

What this service does

Takes a proven mitigation pattern (from upstream defense-generation) and translates it into a control-specific rule for a target technology (Akamai WAF, firewall, or EDR).

Where the input comes from

defense-generation: candidate-produced → mitigation-check: blocked → bypass-validation: no-bypass-found (with at least one executed attempt) → orchestration promotes the candidate to a ProvenMitigationPattern. This service validates the two proof references but does not rerun either proof.

Demo note: the CVE facts below are real, but IDs ending in fixture-1 are illustrative proof lineage. This repository did not execute those upstream proof runs.

Terminal States

translatedSuccess — a candidate rule was generated and passed this service's syntax and conflict checks.
scope-declinedRejected — target is unsupported, input is invalid, or there's a policy conflict.
insufficient-contextMissing data — no policy snapshot available for the target context.
cannot-expressThe target technology cannot represent this mitigation pattern.
malfunctionInternal error — provider failure or result assembly issue.

Live LLM demonstration

The Inference runtime card identifies the active mode, provider, and model without exposing any credential. In a live run, the result panel reports LLM invoked: yes only after the request passes initial scope/context gates and reaches the configured model. Fixture runs report no.

How live AT&T LLM translation works

  1. The browser sends the selected proven mitigation pattern and target-policy context to POST /invoke. API keys remain on the server.
  2. The service first checks target scope, control-class compatibility, and the current policy snapshot. Requests that fail here do not consume an LLM call.
  3. For an eligible request in RUN_MODE=live, the service sends the discriminator, pattern summary, target syntax requirements, and policy summary to AT&T Inference's OpenAI-compatible /chat/completions endpoint.
  4. The model must return a structured candidate. The service parses it and then performs deterministic syntax validation and policy-conflict checks.
  5. Only a candidate that passes those non-LLM gates receives translated. This demo generates a candidate; it never deploys a rule to Akamai, a firewall, or SentinelOne.

How fixture mode differs

With RUN_MODE=fixture, the service skips AT&T Inference completely. It uses local, deterministic per-target templates for the same sample patterns, then runs the same syntax and conflict gates. This mode is best for offline demos, repeatable tests, and showing terminal-state behavior without cost, network access, or model variability.

Choosing a mode: use live mode when you want to demonstrate model-assisted rule construction and the response says LLM invoked: yes. Use fixture mode when you want the exact same output on every run. In both modes, review candidates before deployment and keep the vendor remediation/patch process in place.
